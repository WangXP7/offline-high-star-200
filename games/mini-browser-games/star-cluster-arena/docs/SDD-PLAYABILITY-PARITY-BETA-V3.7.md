# 星团大作战 v3.7.0-beta.2 可玩性与单机规则对齐 SDD

> **已被纠偏规范取代。** 实体体验证明本版本仍使用独立联机玩法执行器，不能视为“单机规则对齐完成”。后续唯一实施依据为 [`SDD-CANONICAL-ENGINE-REBUILD-V3.8.md`](SDD-CANONICAL-ENGINE-REBUILD-V3.8.md)。

## 1. 文档状态

- 状态：代码实施与自动化验收完成，等待实体双机体验验收
- 日期：2026-08-26
- 基线：Git `v3.6.0` / `8c6c95b`
- 版本定位：联机测试版，不覆盖或替换 v3.6.0 正式成品
- 核心原则：自动化通过只代表代码稳定；只有规则、节奏和实体双机体验通过才可称为可玩版本

## 2. 用户实测问题

1. 设置中的“无边框全屏”没有实际改变桌面窗口，首页右下角按钮同样无效；
2. “窗口尺寸”和“画质”的含义不清，用户无法判断哪一项控制显示分辨率、哪一项控制渲染清晰度；
3. 对局中偶发整屏白闪；
4. 联机虽然有十种模式入口，但资源、AI、事件和部分胜负节奏仍与已调好的单机模式不同；
5. 自由模式中资源被服务端瞬间补满，100 个 AI 可在约一分钟内异常膨胀；
6. 当前版本名称和首页文案过度表达了“完全共享”，不符合真实实现程度。

## 3. 已确认根因

### 3.1 桌面桥接未加载与显示状态竞态

- Electron 窗口启用了 `sandbox: true`，旧 `preload.mjs` 却使用 ESM `import`；沙箱预加载按普通脚本执行并抛出语法错误；
- `window.starClusterDesktop` 因此从未注入，首页全屏、设置、退出、复制和外部链接全部绕过了桌面 IPC；F11 属于主进程菜单，所以仍可工作；
- 旧冒烟测试直接调用主进程函数，绕过了真实按钮，因而错误地报告“全屏通过”；
- 渲染进程保存设置后调用 Electron IPC，随后立刻 `location.reload()`；
- 主进程调用 `BrowserWindow.setFullScreen()` 后立即读取并返回状态，没有等待目标状态事件；
- UI 可能得到旧状态，页面重载又会重复应用设置，形成竞态；
- 全屏按钮、设置和 F11 没有通过一个可确认成功/失败的异步状态机。

### 3.2 设置概念混用

- “窗口尺寸”控制桌面窗口客户区大小，不等于渲染清晰度；
- 当前“画质”实际上主要控制内部 Canvas 像素预算和 DPR 上限，更接近“渲染清晰度”；
- v3.7 将 UI 改为明确的“窗口大小”和“渲染清晰度”，并在全屏时说明使用桌面原生输出尺寸。

### 3.3 白闪路径

- 自适应清晰度每隔数秒可能调用 `resize()`；
- 修改 Canvas `width/height` 会清空并重建 2D 与 WebGL 后备缓冲；
- 两层全屏 Canvas 在同一帧重建时可能把尚未绘制的合成表面暴露给窗口；
- 对局中不应通过反复重建后备缓冲降画质，应优先减少阴影、粒子、食点和特效绘制。

### 3.4 联机资源失控

- 单机使用 `foodSpawnBank += dt * foodSpawnRate()`，按每秒预算逐渐补充食点；
- 服务端在每个 30 Hz tick 后用 `while (foods.length < target) spawnFood()` 瞬间补满所有消耗；
- 资源生产量因此不再由模式时间曲线决定，而是由全场吞食速度决定；参与者越多，资源生成越快；
- 服务端事件表也只有三种精简事件，AI 决策器和安全区阶段仍是独立实现。

### 3.5 世界密度与复活刷质量

- 单机世界边长为 7600，服务端却仍使用 5200；相同的 100 个参赛者和 2100 个食点被压缩在约 47% 的面积中；
- 服务端 AI 缺少单机的威胁逃跑与食点优先决策，会让较小 AI 持续撞向追击者；
- 服务端复活没有单机已有的无敌护盾，复活者可被连续秒吃，每次复活又注入一份出生质量；
- 修复前固定种子 60 秒出现 647～706 次击杀、领头 AI 质量约 1.7 万，和单机实测 13 次击杀、领头约 969 质量严重偏离。

## 4. v3.7.0-beta.2 范围

### 4.1 本轮必须完成

1. 首页和联机大厅显示“联机测试版”；
2. 桌面显示模式使用异步状态机，等待实际进入/退出全屏后再返回；
3. 设置只在帧率或渲染清晰度等需要重载的项目变化时重载，显示模式单独切换不得重载页面；
4. 全屏、F11 和设置同步同一实际窗口状态，并显示成功或失败反馈；
5. 明确区分窗口大小、桌面输出尺寸和渲染清晰度；
6. 对局期间固定 Canvas 后备缓冲尺寸，窗口未变化时不得自适应重建；
7. 将食点目标和每秒刷新速率抽到共享玩法内核，单机与权威服务端共同调用；
8. 服务端改用有上限的资源刷新储备池，不得按消费量瞬间补满；
9. 新增一分钟资源注入与最大质量回归测试，覆盖十种模式；
10. 产出独立 beta 成品目录，不覆盖 v3.6.0。

### 4.2 明确不伪装为本轮已完成

- 服务端 AI 尚未直接调用单机完整 AI 决策器；
- 服务端随机事件表尚未完全迁移单机全部事件；
- 安全区多阶段、团队协作、魔王行为和所有模式技能仍需逐项黄金回放；
- beta 只有在后续阶段完成这些迁移并通过实体双机测试后才能转为正式版。

## 5. 目标架构

```text
单机页面 ─┐
          ├─ Canonical Mode Catalog
权威服务 ─┤  Canonical Food / Movement / Collision Rules
          └─ Canonical Event / AI Rules（后续逐项迁移）

LocalAuthority   = 本机 60 Hz 驱动共享规则
NetworkAuthority = 房主 30 Hz 驱动同一规则并发送快照
```

不要求单机和联机使用同一个大循环文件；要求所有会改变结果的纯规则只有一个实现。渲染、网络编码、插值和预测允许各自独立。

## 6. 共享资源规范

共享函数输入必须显式包含：

- 模式配置；
- 已经过时间；
- 安全区阶段；
- 当前事件倍率；
- 基础食点数和最大食点数。

共享函数输出：

- 当前目标食点数；
- 当前每秒食点生成预算。

服务端每 tick：

1. 处理被吃掉的食点；
2. 计算当前目标；
3. `spawnBank += dt * rate`；
4. 本 tick 只生成 `floor(spawnBank)`，且受单 tick 上限和目标缺口限制；
5. 未使用预算留在储备池，但储备池必须有上限，避免暂停后爆发生成。

## 7. 显示与清晰度规范

| 设置 | 含义 | 是否影响玩法 |
| --- | --- | --- |
| 窗口化 / 无边框全屏 | Windows 窗口呈现方式 | 否 |
| 窗口大小 | 仅窗口化时的客户区尺寸 | 否 |
| 渲染清晰度 | Canvas 像素预算/DPR 上限 | 否 |
| 图形帧率 | 每秒呈现帧数上限 | 否 |

- 无边框全屏始终使用当前显示器原生桌面尺寸；
- 不提供伪造的“全屏分辨率切换”，除非未来实现真正的独占全屏；
- 对局中可动态降低特效复杂度，但不动态重建全屏 Canvas；
- Canvas 重建后第一帧必须先填充游戏深色背景，避免透明/白色中间帧。

## 8. 验收门禁

### 自动化

- 显示状态请求只有在实际状态匹配后返回成功；
- 单机和服务端在相同模式、时间、阶段和事件倍率下得到相同食点目标与刷新率；
- 十模式 60 秒资源注入量有固定上限；
- 自由模式 100 参与者 60 秒压力中不得因瞬时补满产生无限资源；
- 原有协议、房间、快照、规则和十模式测试全部通过。

### 桌面冒烟

- 设置切换全屏、首页按钮和 F11 各完成进入与退出；
- 返回状态、窗口实际状态和设置选中项一致；
- 1920×1080、1440×900 窗口切换后页面可用；
- 对局至少运行 60 秒，Canvas 后备缓冲重建计数在窗口不变时为 0；
- 单机和联机性能采样继续达到 55 FPS 最低门槛。

### 人工双机

- 两台电脑互换房主；
- 自由模式运行 5 分钟，记录前十名质量曲线；
- 霸屏、大逃杀、团队、孢子和魔王各抽验至少一局；
- 对比同模式单机的资源密度、首个巨球出现时间、AI 分裂频率和胜负时间；
- 未通过前保留“联机测试版”标签，不发布为正式稳定版。

## 10. 成熟实现参考与取舍

- [Electron BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window/) 要求依赖 `enter-full-screen` / `leave-full-screen` 确认异步全屏状态；本项目因此不再把函数调用完成当作切换成功；
- [Unity FullScreenMode](https://docs.unity3d.com/ja/current/ScriptReference/FullScreenMode.html) 将窗口化、全屏窗口和独占全屏视为不同模式；Electron 没有可靠的 Windows 独占分辨率切换，因此本项目只提供“窗口化”和“无边框全屏”，不伪造独占全屏选项；
- [Unreal Networking Overview](https://dev.epicgames.com/documentation/unreal-engine/networking-overview-for-unreal-engine?lang=en-US) 采用服务端权威状态，[Networked Movement](https://dev.epicgames.com/documentation/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine?lang=en-US) 说明客户端渲染频率高于网络更新率时必须插值而非直接跳点；本项目继续采用房主权威、输入上报、本地预测和远端插值，而不是让两台电脑各自计算碰撞结果。
