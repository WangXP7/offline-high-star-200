# 星团大作战：共享规则内核与性能升级 SDD v3.3

状态：第一阶段发布候选实施记录
日期：2026-08-25
适用范围：`star-cluster-arena/` 前后端源码版与 Windows 桌面封装版
明确不修改：仓库根目录的单 HTML 版本 `ball-arena.html`

## 1. 背景与根因

v3.2 已实现局域网发现、房间、十模式入口、服务端权威状态、快照插值和桌面封装，但存在两个结构性问题：

1. 单机 `frontend/js/game.js` 与联机 `backend/multiplayer/simulation-v2.mjs` 各自维护移动、分裂、半径、模式参数和部分胜负规则，联机实际成为第二套简化游戏。
2. 单机把 60 Hz 模拟、AI、碰撞与 Canvas 2D 前景渲染放在同一主线程；WebGL 背景又被复制回 2D 画布，独显能力没有转化成对应收益。

v3.3 不再以“给联机补一个相似规则”为目标，而以“单机规则是产品基准、共享内核是唯一实现”为约束。

## 2. 外部方案调研结论

商业版《球球大作战》的服务端源码和内部网络协议没有公开，不能把推测描述成官方实现。本设计采用公开、可验证的同类和通用实时联机方案：

- MultiOgar 在权威服务器上接收世界坐标鼠标目标；每个细胞分别计算到目标的距离、方向和由大小决定的速度，并使用四叉树查询视野和碰撞候选。
- 开源 Agar.io Clone 将游戏规则放在服务端，客户端负责输入和画面。
- Valve/Gabriel Gambetta 模型采用服务端权威、本机预测与输入确认/重放、其他实体插值；低频快照不应直接驱动跳跃式显示。
- Electron 官方提供 `force_high_performance_gpu`；它用于多 GPU 设备优先离散 GPU，但不能替代主线程性能优化。

对应到本项目的决策：

1. 客户端发送世界坐标目标 `targetX/targetY`，不再只发送归一化方向。
2. 单机、服务端和本机预测调用同一移动函数及同一常量。
3. 服务端仍是吞噬、分裂、技能、积分与胜负的最终裁判。
4. 本机预测只预测可复现的本地运动；远端实体继续按服务器时间插值。
5. 网络按视野/相关性演进，不能以无限制广播全世界对象作为长期方案。

## 3. 目标与非目标

### 3.1 本轮目标

- 建立浏览器和 Node 均可加载的共享玩法内核。
- 共享半径、移动速度、鼠标距离减速、转向、阻尼、分裂阈值和分裂冲量。
- 联机输入升级为世界坐标目标，并保留方向字段作诊断和兼容回退。
- 客户端预测与服务端使用相同运动积分器、模式速度和事件速度。
- 单机十模式的静态配置成为联机模式配置的来源，局域网人数缩放作为显式适配层存在。
- 删除 WebGL 背景到 Canvas 2D 的逐帧复制，改为真正的双画布分层合成。
- 单机掉帧时允许有迟滞的分辨率降档，避免长期维持过高像素倍率。
- Electron 优先高性能 GPU，并把真实显示器刷新率传给游戏。
- 增加跨单机/联机运动等价测试、协议测试和性能守护测试。

### 3.2 后续迁移目标

- 将十模式的动态规则依次迁入共享规则模块：团队接分身、面积霸屏、完整随机事件、魔王模板与技能。
- 将单机 AI 决策拆为低频调度，并评估移入 Worker；碰撞和最终状态仍保持固定步进。
- 引入服务端兴趣管理，只给每个客户端发送视野内动态实体及必要全局目标。

### 3.3 非目标

- 不宣称复刻商业《球球大作战》的私有协议或服务端源码。
- 不把 5070 Ti/5060 的高占用率当成目标；目标是稳定帧时间和一致手感。
- 不在 v3.3 第一阶段一次性重写全部 UI、商城、外观和 AI。
- 不修改单 HTML 版本。

## 4. 目标架构

```text
鼠标/触摸目标
     │
     ├── 单机 game.js ─────────────┐
     │                             │
     └── 联机输入 targetX/targetY  │
                    │              │
                    ▼              ▼
             权威服务器      共享 gameplay-core
                    │              ▲
                    ├── ACK/快照 ──┤ 本机预测
                    └── 远端状态 ───► 快照插值
```

共享内核必须满足：

- 无 DOM、无 Electron、无网络、无存储依赖。
- 同一输入、初始状态、`dt` 和速度修正得到同一运动结果。
- 常量只定义一次；调用方只能传模式/事件乘数和角色转向参数。
- 所有函数为纯函数或显式修改传入实体，便于单元测试。

## 5. 规范化输入

联机输入：

```json
{
  "type": "input",
  "seq": 123,
  "targetX": 3812.4,
  "targetY": 1960.8,
  "dx": 0.91,
  "dy": -0.41,
  "split": false,
  "eject": false,
  "quickMerge": false,
  "special": false
}
```

- `targetX/targetY` 是当前摄像机下指针对应的世界坐标。
- 服务端将目标限制到合理世界扩展边界，拒绝非有限值。
- 每个细胞分别计算 `target - cell.position`，因此分身位置不同时速度和收敛过程也不同。
- `dx/dy` 仅用于旧输入回退、断线 AI 和诊断；新客户端的运动以目标坐标为准。
- `seq` 单调递增；快照携带已处理输入序号。
- 世界目标和共享预测公式与 v2 客户端不兼容，因此握手协议升级为 `sca-lan-v3`；不同协议版本不得进入同一房间。

## 6. 共享运动契约

基准保持原单机手感：

| 参数 | 规范值 |
|---|---:|
| 速度分子 | `352` |
| 半径除数 | `96` |
| 满速目标距离 | `210` |
| 最小距离倍率 | `0.08` |
| 真人转向率 | `4.35` |
| 普通 AI 转向率 | `3.35` |
| 60 Hz 阻尼 | `0.965` |
| 最小分裂质量 | `32` |
| 最小吐球质量 | `30` |
| 分裂冲量 | `650` |

运动步骤顺序固定为：目标向量 → 距离倍率 → 大小速度 → 模式/事件倍率 → 指数转向 → 与 `dt` 对齐的阻尼 → 积分 → 世界边界。

服务端可保持 20 Hz，客户端可按小段重放；因为转向和阻尼均按 `dt` 换算，不再把 20 Hz 常量硬编码成另一套手感。

## 7. 模式规则来源

- 共享目录保存十模式规范化静态定义。
- 单机直接读取该定义。
- 联机 `modes.mjs` 从规范定义派生网络配置，只能增加 `minimumHumans`、`maximumBots`、`recommendedParticipants` 等部署字段。
- 局域网人数不足时允许缩放活动队伍数，但原始 `teams/teamSize/players` 必须保留为规范元数据。
- 任何有意差异必须写入 `lanAdaptation`，不得静默改变描述和规则。

动态规则迁移顺序：

1. 移动、分裂、吐球、合球。
2. 生存/逃杀/闪电的生命、安全区与制霸。
3. 孢子和病毒。
4. 霸屏/巨行星的实际区域覆盖率。
5. 据点。
6. 团队接分身。
7. 魔王模板、技能和 AI。

未完成迁移的模式必须在诊断中标记 `parity: partial`，不能宣称完全照搬。

## 8. 同步与校正

- 权威模拟：20 Hz 固定步进，事件循环追赶有上限。
- 输入：30 Hz，按钮动作边沿不得因覆盖而丢失。
- 快照：20 Hz；静态大对象使用基线/增量。
- 本机：使用共享运动积分器预测到估算服务器时间，最多领先 180 ms。
- 校正：收到 ACK 后删除已确认输入，从权威状态重放剩余输入。
- 小误差在短时间内视觉收敛，大误差立即权威纠正；逻辑状态永远不插值伪造。
- 远端：按自适应缓冲延迟插值，不使用本机输入预测。
- 模式/事件速度倍率必须进入快照并参与本机预测。

## 9. 性能设计

### 9.1 渲染

- `gpuCanvas` 保持不透明 WebGL 背景和食点层。
- `gameCanvas` 改为透明 Canvas 2D 前景层，不再把 GPU 画面复制到离屏 2D 再复制回来。
- 前景只绘制病毒、细胞、文字和特效。
- 根据平均帧时间使用迟滞降档：连续压力时降低前景像素倍率，稳定后缓慢恢复。
- 低画质减少阴影、径向渐变、内环和远端外观，但玩家自身轮廓和必要信息不消失。

### 9.2 模拟

- 固定步进不与显示器刷新率绑定。
- AI 思考、排行榜、食物补充等非碰撞任务按各自频率调度。
- 空间索引复用，禁止在同一模拟步无理由重复全量构建。
- 长帧后最多补算有限步骤；记录丢弃时间，作为性能回归指标。

### 9.3 桌面

- Electron 启动前设置官方 `force_high_performance_gpu`。
- 保留 GPU rasterization/zero-copy，不使用 `disable-gpu`。
- 从当前显示器读取 `displayFrequency`，通过 `refresh` 参数传入。
- UI 显示 WebGL 后端、实际适配器、渲染倍率、物理频率和目标 FPS。
- 若仍选择集显，提示用户在 Windows“图形设置”中把程序设为高性能；程序不静默修改系统设置。

## 10. 测试规范

### 10.1 单元与契约

- 相同半径、目标、速度、`dt`、模式倍率在单机适配器、服务端和预测器产生一致结果。
- 大细胞速度严格小于小细胞。
- 同一玩家不同位置的分身向同一世界目标运动时，方向和距离倍率各自计算。
- 目标接近细胞时减速，远离时满速。
- 分裂阈值和冲量一致。
- 十模式公共静态字段来自同一规范对象。

### 10.2 网络

- 非有限/极端目标坐标被安全处理。
- ACK 后只重放未确认输入。
- 随机事件速度倍率下，预测与权威轨迹保持在误差预算内。
- 20/50/100 ms RTT 与 0/10/30 ms 抖动下，本机无周期闪现，远端连续。

### 10.3 性能门槛

- 1440×900、100 星团大逃杀：进入对局 30 秒后平均渲染不低于 55 FPS，1% low 不低于 40 FPS；未达标必须保留遥测并不得描述为完成。
- 单帧模拟追赶不超过 3 步，不出现无限时间螺旋。
- GPU 双画布路径不得执行 WebGL → 2D 的逐帧背景复制。
- 8 参与者联机房间运行 30 分钟，无持续 `bufferedAmount` 增长、无实体泄漏。

### 10.4 真机

1. 5070 Ti 与 5060 两端分别建房一次。
2. 自由模式用大小不等的多个分身绕鼠标、近距离收球、快速反向，录像对照单机。
3. 十模式各完成一次专属胜负或关键技能。
4. 检查两端顶部适配器名称；若不是 RTX，记录 Windows 图形首选项。
5. 有线/Wi-Fi 各测一次，记录 RTT、抖动、快照率和 FPS。

## 11. 发布门槛与回滚

- `npm run check`、全部单元/集成/模式测试、长稳测试通过。
- 单机和联机移动等价测试必须存在，不能只验证“数值有限”。
- 桌面开发态与打包态 GPU/刷新率冒烟通过。
- 新安装版和便携 ZIP 输出到 `../star-cluster-arena-desktop/`，旧成品在新构建成功前不覆盖。
- 真机十模式未完成时必须标记候选版，不推送 GitHub Release。
- 按共享内核、输入协议、渲染、桌面、模式迁移分开提交，任一阶段可独立回滚。

## 12. 完成定义

v3.3 第一阶段完成必须同时满足：

- 单机、权威服务器和预测器共享同一移动/分裂常量与函数。
- 联机发送世界坐标目标，大小不等分身不再表现为统一方向满速平移。
- 单机 WebGL 背景不再逐帧复制进 2D 前景。
- Electron 优先独显并传递实际刷新率。
- 新契约测试、协议测试、现有测试和桌面冒烟全部通过。
- 文档明确十模式动态规则的已迁移/待迁移状态，不把部分等价包装为完全等价。

## 13. 第一阶段实施结果

- `game-mode-catalog.js` 已成为单机和服务端共同读取的十模式基础目录；局域网人数、队伍缩放和说明保留在 `lanAdaptation`，不再复制基础标签、时长、起始质量和倍率。
- `gameplay-core.js` 已由单机、权威模拟和本机预测共同调用；输入协议升级为 `sca-lan-v3`。
- 项目检查通过：18 个关键文件、25 个脚本语法有效；全量自动化 98/98 通过，真实双客户端集成流程 5/5 通过。
- 十模式 8 参与者发布档和 16 参与者压力档各运行 1200 tick；动态快照 p95 最高分别为 5.4 KiB 和 12.7 KiB，服务端 tick p95 最高 0.105 ms。
- 浏览器人工冒烟无脚本错误或 WebGL 警告；同一 AMD 核显测试面在 100 星团大逃杀活动期观察到约 53～54 FPS，比修改前约 40 FPS 明显改善，但不替代目标机器的 1440×900 长稳验收。
- Electron 开发态和打包态均识别到 `NVIDIA GeForce RTX 5070 Ti / D3D11` 与 160 Hz 显示器；首页、联机大厅和内置服务冒烟通过。
- 十模式动态规则仍标记为 `parity: partial`；两台目标电脑逐模式真机验收未自动完成，因此 v3.3 保持发布候选，不推送 GitHub Release。
